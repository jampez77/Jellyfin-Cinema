# ScreenHarbour 0.2.29 — prerelease

Cinema Mode trailer buttons no longer depend on visiting the next video and going back. Jellyfin 12 does not retain the playback queue sent in its initial Start/Progress reports; it saves that queue only after a Stop report. ScreenHarbour now retains the authenticated current device's reported queue for its trailer and in-player navigation features. This lets **Skip trailer** and **Add to watchlist** resolve the first trailer, including when it is paused.

This addresses the real-server failure remaining in 0.2.28. A live Jellyfin 12 browser reproduced the missing initial controls and confirmed that, once Next/Back made the queue available, the controls remained visible over the pause screen after the native controls faded. Earlier fixtures had incorrectly populated the native queue before any stop event.

Both trailer buttons now sit on the **left**, below the pause-screen details and above Jellyfin's playback controls. They stay in that position while paused even when the native controls fade away. **Skip trailer** receives focus when each trailer’s buttons first appear, so Select skips immediately. Subsequent polling, pausing and watchlist updates preserve the user’s chosen focus.

The **Browse** icon also disappears immediately when Jellyfin switches to TV layout, even if playback metadata is still loading. Press **Down** from the playback controls to open in-player browsing. The existing fix that keeps the next video playing after Skip is preserved.

## Update

Update **ScreenHarbour**, restart Jellyfin, then fully reload the browser or close and reopen the web-based TV client. Keep **File Transformation** enabled. Saved settings and plugin identity are preserved.

## Validation scope

- TypeScript typecheck and 191 unit tests passed.
- 42 trailer, pause-screen, initial-load and demo browser checks passed; 47 player-browser and channel-zapper checks passed.
- Layout checks cover 1440×900, 1920×1080 and 1280×600 with native and ElegantFin styling, long descriptions, watchlist feedback and faded playback controls.
- All 308 server verification assertions passed against each supported Jellyfin target: 10.10.7, 10.11.0 and 12.0.0. The 10.10.7 checks compiled for .NET 8 and ran with runtime roll-forward on the locally available newer runtime.
- Server checks exercise native report model binding and filter registration, the empty initial Jellyfin 12 queue, overlapping Start/paused Progress reports, user/device isolation, stale-queue rejection, expiry and bounded storage.

Automated server checks use a temporary HTTP host and version-specific Jellyfin types. Browser checks simulate media transport. The revised package has not been installed on the production Mac mini, and physical TV testing remains pending.
